## Remediation status

- **Commit 1 (clear-cut fixes):** H1, M2, M4, M5, M6, M9, L4, L7, D1 — each with tests.

  gamification counts from account-tab-badge counts in `server/util/accountCounts.js`:
  - New `getGamificationCountsFor()` powers XP / level / achievements from **visibility-filtered**
    counts — only publicly-published recipes (`RECIPE_VISIBLE`) count as "Published N recipes"; only
    real, non-hidden written reviews (non-empty `reviewText` + `REVIEW_VISIBLE`) count as "Left N

    frame non-revocation as the bug, and derived (unstored) counts make it the simplest correct model.

## Confirmed findings

### High

#### H1 — `DELETE /collections/:id` 500s and the collection becomes permanently undeletable when the user's `userRecipeData` doc has no `savedRecipes` field
- **File:** `server/routes/collections.js:231`
- **Subsystem:** saved-recipes
- **What's wrong:** The delete route runs a single `updateOne` with
  `$pull: { collections: { id }, 'savedRecipes.$[].collectionIds': id }`. The all-positional `$[]`
  operator requires the `savedRecipes` path to **exist** on the document; if it's absent, MongoDB
  rejects the whole update (code 2, "The path 'savedRecipes' must exist in the document in order to
  apply array updates"), so **neither** `$pull` applies and `asyncHandler` surfaces a 500. A
  `savedRecipes`-less doc is a shape this same file creates: `POST /collections` upserts
  `{ $setOnInsert: { collections: [] } }` (line 135) for a first-time user, and `POST /madeRecipe`
  (`server/routes/recipes.js:946`) does the same via `$addToSet` + `upsert`.
- **Failure scenario:** A signed-in user whose first-ever `userRecipeData` write is creating a
  collection gets a doc `{ _id, collections: [{...}] }` with no `savedRecipes` field. Every later
  `DELETE /api/collections/:id` returns 500 and shows "Could not delete collection." The collection
  is permanently undeletable until the user happens to save any recipe (which finally creates the
  `savedRecipes` array).
- **Repro:**
  1. With no existing `userRecipeData` doc for the user: `POST /api/collections {name:'A'}` → 201.
  2. `DELETE /api/collections/<id>` → 500, collection still present.
  - (Confirmed against `mongodb-memory-server`: the exact update errors; an empty `savedRecipes: []`
    array succeeds, so only the missing-field shape fails. All existing `collections.test.js` fixtures
    seed a `savedRecipes` array, which is why the suite never hits it.)

### Medium

#### M1 — `editRecipe` returns the unprojected recipe doc, leaking internal admin moderation/curation stamps to the non-admin owner
- **File:** `server/routes/recipes.js:643`
- **Subsystem:** recipe-crud
- **What's wrong:** `PUT /editRecipe` does `findOneAndUpdate(..., { returnDocument: 'after' })` with
  **no projection** (lines 643–647) and returns the raw doc via `res.json(updated)` (line 660). Every
  other public recipe read strips `RECIPE_INTERNAL_STAMPS` via `publicRecipeProjection`
  (`server/util/recipeFields.js:51-58`, which states these "carry admin Firebase uids … so they must
  never reach a non-admin caller"). The edit route bypasses that whitelist, so the response includes
  `moderatedBy/moderatedAt/featuredBy/featuredAt/publishUpdatedBy/publishUpdatedAt` whenever an admin
  has ever moderated/featured/unpublished the recipe. The client caches this into `['recipe', id]`
  (`src/pages/AddRecipe/useRecipeForm.ts:428`).
- **Failure scenario:** An admin features/hides user X's recipe (stamping `featuredBy = adminUid`).
  X later edits it; the 200 response body contains the admin's Firebase uid — the exact disclosure the
  public projections prevent.
- **Repro:**
  1. As admin, feature or moderate a recipe owned by user X.
  2. As X, `PUT /api/editRecipe?recipeId=:id` with a valid edit payload.
  3. Inspect the JSON response — it contains `featuredBy/featuredAt` (and `moderatedBy/moderatedAt`).
- **Note:** `docs/API_CONTRACT.md:307` already lists this in its DRIFT section as inconsistent with the
  whitelist rationale — a known-but-unfixed gap.

#### M2 — Recipe cards render "$0.00/serving" when `servingPrice` is the `0` "unknown" sentinel
- **File:** `src/Components/RecipeCard/RecipeCard.tsx:89`
- **Subsystem:** serving-price
- **What's wrong:** `calculateServingPrice` returns `0` both for genuinely-free and for
  no-price-data (every ingredient's enrichment missed → server omits `totalPriceUSACents`). The
  detail page and summary bar treat `0` as unknown and hide it (`SingleRecipe.tsx:154`
  `hasPrice = servPrice > 0`; `AddRecipeSummaryBar.tsx:77` shows "—"), but **every card surface** gates
  only on `!= null`: `RecipeCard.tsx:89`, `HomeRecipeCard.tsx:36`, `HomeCookSuggestion.tsx:82`,
  `HomeBrowseByMeal.tsx:30`, `UserRecipeThumbnail.tsx:40`, `PublicProfile.tsx:368`. `formatPrice(0)`
  = "$0.00". These recipes also sort **first** under the browse "cheapest" order
  (`server/routes/recipes.js:126`).
- **Failure scenario:** A user adds an ingredient whose enrichment soft-fails (a designed path — the
  toast says "added without nutrition data"), and publishes (validation allows it). Every
  browse/home/profile card shows "$0.00/serving" for a recipe that costs real money, and it pins to
  the top of "cheapest." The recipe's own detail page hides the price while its card claims $0.00.
- **Repro:** Create a recipe with an obscure ingredient that misses enrichment (row shows "—"),
  publish, then open `/recipes` browse or a home row → card shows "$0.00/serving"; sort by "cheapest"
  → it's first.
- **Fix direction:** Card surfaces should gate on `servingPrice > 0`, matching the detail page.

#### M3 — Submitting while ingredient enrichment is in flight permanently persists `ingredientData: null` and an understated `servingPrice`
- **File:** `src/pages/AddRecipe/useRecipeForm.ts:389`
- **Subsystem:** serving-price
- **What's wrong:** The add flow inserts ingredients optimistically with `ingredientData: null`
  (`IngredientsContainer.tsx:97-102`) and fills price/image when async enrichment resolves (up to 12s
  later). Nothing gates submit on rows still loading: `validateRecipeForm` only checks
  `ingredients.length > 0` and never the per-row enrichment status (`statusById` lives privately in
  `IngredientsContainer` and is never lifted), and the submit button is disabled only by
  `addRecipeLoading`. If the user clicks Create inside that window, `calculateServingPrice` skips the
  null row and the recipe is posted with that ingredient stored as `ingredientData: null` **forever**;
  the enrichment that arrives moments later only updates discarded local state.
- **Failure scenario:** User types their last (priciest) ingredient and clicks Create ~1–2s later
  while the price cell still shows the loading skeleton. The published doc permanently lacks that
  ingredient's price/image and the stored `servingPrice` excludes it (e.g. a $14 recipe publishes as
  "$2.10/serving"). Nothing heals the doc short of the owner re-editing.
- **Repro:** On `/add-recipe`, add an ingredient; while its price cell shows the skeleton (throttle
  the network), click Create; inspect the created doc — the ingredient has no image/price and
  `servingPrice` omits it.
- **Fix direction:** Gate submit while any row's enrichment is in flight (lift enrichment status to the
  form, or block on it).

#### M4 — Unguarded `localStorage` `JSON.parse` in `SingleRecipe` crashes every recipe page to the global error fallback
- **File:** `src/pages/SingleRecipe/SingleRecipe.tsx:124`
- **Subsystem:** serving-price
- **What's wrong:** The servings-persistence effects read/parse `localStorage` with no try/catch and no
  shape validation, on every recipe load: `JSON.parse(localStorage.getItem('recipeServings') || '[]')`
  then `.find(...)` (lines 122–130), plus `updateRecipeLocalStorage` (102–110). Three unhandled throws:
  (a) `window.localStorage` throws `SecurityError` when the browser blocks site data (Chrome "Block
  all cookies", some webviews); (b) `JSON.parse` throws on a corrupt value; (c) a valid-JSON
  non-array (e.g. `{}`) makes `.find`/`.findIndex` throw `TypeError`. An effect throw unwinds to the
  app-wide `Sentry.ErrorBoundary` (`src/App.tsx:129`), blanking the whole page to `AppErrorFallback`.
  The repo's own convention guards this — `src/util/savedFilters.ts:14` wraps all localStorage access
  defensively; `SingleRecipe` is the **only** unguarded localStorage use in `src/`.
- **Failure scenario:** A visitor with "Block all cookies" opens any recipe URL → the effect touches
  `window.localStorage` → `SecurityError` → app-wide error screen instead of the recipe, for every
  recipe on every visit. Equivalently, a corrupt `recipeServings` value crashes every recipe page
  until the user manually clears site data.
- **Repro:** In devtools: `localStorage.setItem('recipeServings','{')` then reload a recipe page →
  `AppErrorFallback`. Or set Chrome to "Block all cookies" and open any `/recipes/:id`.
- **Fix direction:** Wrap the reads in try/catch + `Array.isArray` validation, mirroring
  `savedFilters.ts`.

#### M5 — `PATCH /reports/:id` closes reports without the `status: 'open'` guard, allowing re-close, status-flip, and re-triggering the automod restore guard
- **File:** `server/routes/reports.js:314`
- **Subsystem:** moderation
- **What's wrong:** The single-report close route does `findOneAndUpdate({ _id }, { $set: { status,
  resolvedBy, resolvedAt } })` with **no** `status: 'open'` filter. The bulk route (line 263) and both
  bugReport routes enforce open-only — `bugReports.js:194` even documents why. Every re-PATCH of an
  already-closed report overwrites `resolvedBy/resolvedAt`, writes a second `report.resolve`/`.dismiss`
  audit row (line 320), re-sends the "report resolved" email (line 332), and re-runs
  `restoreHeldRecipe` (line 330).
- **Failure scenario:** Two admins on a stale Open tab; A resolves report X; B clicks Dismiss on X →
  X flips resolved→dismissed, A's attribution is overwritten, a contradictory audit row is written,
  metrics shift. **Worse:** X is a closed automod report whose recipe was later re-held (owner
  re-edit → new open report + `pending_review`); B re-resolves stale X → `restoreHeldRecipe` finds the
  recipe at `pending_review` and flips it to `active`, **publishing currently-held content** while its
  new automod report still sits open.
- **Repro:** `PATCH /api/reports/:id {status:'resolved'}` on an open report, then `PATCH` the same id
  with `{status:'dismissed'}` → 200, status flips, attribution overwritten, duplicate audit row.
- **Note:** `docs/API_CONTRACT.md:773` lists this as "a protection `PATCH /reports/:id` does not have."
- **Fix direction:** Add `status: 'open'` to the filter and return 409 on no-match, matching the bulk
  and bugReport routes.

#### M6 — Admin user list never counts open `'user'`-type reports: the `openReports` tally drops profile reports on the floor
- **File:** `server/routes/admin.js:140`
- **Subsystem:** moderation
- **What's wrong:** `enrichUsers` fetches open reports with `$or: [{ reportedUsername: {$in} }, {
  recipeId: {$in} }]` (which matches `targetType: 'user'` reports), but the per-uid tally is
  `rep.targetType === 'review' ? uidByUsername[rep.reportedUsername] :
  ownerByRecipeId[String(rep.recipeId)]`. A `'user'` report falls into the else branch, has no
  `recipeId` (`reports.js:157` omits it for user targets), so `ownerByRecipeId['undefined']` is
  undefined and the report is silently skipped — even though the report carries an unused
  `reportedUid`.
- **Failure scenario:** Several users file "Report user" against @spammer (who has no recipes/reviews).
  `GET /admin/users` and `GET /admin/users/:uid` both render `counts.openReports: 0` for @spammer, so
  the admin list — the surface meant to prioritize who to suspend/ban — shows the reported account as
  clean while the reports queue holds open reports against them.
- **Repro:** `POST /api/reports {targetType:'user', reportedUsername:'spammer', reason:'spam'}`, then
  `GET /api/admin/users?query=spammer` → `openReports` is 0.
- **Fix direction:** Tally `'user'` reports by `reportedUid` (already snapshotted on the report).

#### M7 — Public profile leaks existence of hidden/held recipes through gamification level and achievement badges
- **File:** `server/routes/publicProfile.js:97`
- **Subsystem:** gamification
- **What's wrong:** `GET /getPublicProfile` deliberately filters everything recipe-related through
  `RECIPE_VISIBLE` (its own comment at lines 53–56: counting only visible recipes "avoids leaking the
  existence of held/hidden recipes … `getAccountCountsFor` is unfiltered … it would inflate these
  public totals"). Yet line 97 feeds those **unfiltered** counts into `computeGamification(counts, [])`
  and publishes the resulting `level/rank/xp/pct` and earned achievement badges (106–111).
  `counts.recipes` is `countDocuments({ userId })` with no status filter, so withheld recipes still
  award 100 XP each and satisfy `first_recipe`/`prolific`. This is an **unauthenticated** endpoint.
- **Failure scenario:** A user's first recipe is auto-held as `pending_review` (or an admin hides it).
  Their public profile shows "Recipes: 0" with an empty grid, but simultaneously shows the "First
  Recipe" badge and a level/XP that includes the withheld recipe. Any anonymous visitor learns a
  moderation-hidden recipe exists — exactly the leak the visible-only aggregate was written to prevent.
- **Repro:** Have user A's recipe held/hidden, then anonymously `GET
  /api/getPublicProfile?username=A` → `recipesTotalCount: 0`, `recipes: []`, but `achievements`
  contains `{ id: 'first_recipe', earned: true }` and level/xp include the invisible recipe.
- **Note:** Confirmed on 2/2 skeptic votes (the third skeptic died on the session limit); both were
  affirmative.
- **Fix direction:** Compute gamification from visibility-filtered counts on this public path.

#### M8 — `usePaginatedLoadMore` appends the current page's items a second time when a `page>0` query refetches, duplicating saved-grid cards
- **File:** `src/pages/Account/usePaginatedLoadMore.ts:89`
- **Subsystem:** saved-recipes
- **What's wrong:** The accumulate effect is keyed on `data` alone and for `page > 0` unconditionally
  does `const updated = [...items, ...data.items]`. `items` already contains that page's items, so any
  re-resolution of the same page-N query with structurally different data re-appends the whole page.
  The app's `QueryClient` is a bare `new QueryClient()` (`src/index.tsx:21`) — `staleTime 0`,
  `refetchOnWindowFocus true` — so the observed page-N query refetches on every window focus, and any
  changed projected field (e.g. a `rating` update) yields a new `data` reference. Affects all
  consumers: Saved / Ratings / Your Recipes tabs and the SingleRecipe reviews list.
- **Failure scenario:** User opens Saved (12 recipes), clicks Load more (page 1, 12 cards), switches
  windows; someone rates a page-1 recipe; on refocus the page-1 query refetches with changed data →
  the effect appends page-1's items again → 18 cards with 6 duplicates + duplicate-key warnings, and
  `isMore` is miscomputed against the inflated length.
- **Repro:** Load Saved with >6 recipes, click Load more, blur the window, change a projected field of
  a page-1 recipe (e.g. rate it from another account), refocus.
- **Fix direction:** Track which pages have been appended (or dedupe by `_id`) instead of keying the
  append purely on `data`.

#### M9 — `AddToCollectionPopover`: a failed membership load leaves all boxes unchecked, and the next toggle silently wipes the recipe's existing collection memberships
- **File:** `src/Components/AddToCollection/AddToCollectionPopover.tsx:36`
- **Subsystem:** saved-recipes
- **What's wrong:** The mount effect calls `RecipeAPI.getSavedRecipe(recipeId).then(...).finally(...)`
  with **no `.catch`**. If the request fails, `selected` stays the empty Set while `.finally` clears
  `loading`, so the popover renders as if the recipe belongs to no collections (and the rejection
  escapes as an unhandled promise rejection). Because `persist` sends the **full** membership set
  (`setRecipeCollections` → server `$set savedRecipes.$.collectionIds`), the first checkbox the user
  toggles from this bogus empty baseline replaces the whole server-side membership array with just
  that one id.
- **Failure scenario:** Recipe is in collections A and B. User opens the popover while
  `GET /getSavedRecipe` fails (transient blip); popover shows A and B unchecked. User checks C → PATCH
  sends `collectionIds: ['C']` → server overwrites `['A','B']` with `['C']`. The recipe drops out of A
  and B silently — no error, no toast.
- **Repro:** Open the popover for a recipe filed in two collections with `getSavedRecipe` forced to
  fail, then check any collection.
- **Fix direction:** Add a `.catch` that surfaces the error and blocks toggles until membership is
  known (every other async path in this component already has catch + toast + rollback).

### Low

#### L1 — Negative `?page` produces a negative Mongo `.skip()` and 500s the browse/created-recipes endpoints
- **File:** `server/routes/recipes.js:61` (also `server/routes/users.js:85`)
- **Subsystem:** recipe-crud
- **What's wrong:** `skip = (parseInt(page) || 0) * limit` with no floor; a negative `page` yields a
  negative skip, which MongoDB rejects → `asyncHandler` → 500. `publicProfile.js:150` guards the same
  param with `Math.max(0, …)`; the safe pattern just wasn't applied here.
- **Repro:** `curl 'http://localhost:4000/api/recipes?page=-1'` → 500.
- **Note:** Documented in `docs/API_CONTRACT.md` DRIFT ("No client sends one; direct API callers can
  trigger a 500"). The intent skeptic voted this a known-accepted wart, but code+reach confirmed it.

#### L2 — Client-supplied `servingPrice` is persisted verbatim and drives the cheapest/expensive sort, allowing price spoofing and sort gaming
- **File:** `server/routes/recipes.js:548`
- **Subsystem:** recipe-crud
- **What's wrong:** `servingPrice` is in `CREATABLE`/`EDITABLE_RECIPE_FIELDS`, copied straight from the
  request body, bounded only to `[0, 1_000_000]` cents, and never recomputed server-side. The same
  value is the sort key for cheapest/expensive and the displayed price.
- **Repro:** Authenticated `POST /api/addRecipe` with `servingPrice: 0` on an expensive recipe →
  stored as free, shown as $0.00, sorts first under `order=cheapest`.
- **Note:** The intent skeptic classifies this as deliberate (server can't recompute price without
  re-running external enrichment; treated as ordinary UGC misrepresentation handled by moderation).
  Code+reach confirmed the mechanism; weigh the fix against that intent.

#### L3 — Server never requires `servings` (and trusts client-computed `servingPrice`), letting a crafted create render "$NaN total" to all viewers
- **File:** `server/util/recipeLimits.js:59`
- **Subsystem:** serving-price
- **What's wrong:** `REQUIRED_RECIPE_FIELDS` is only `['title','ingredients','instructions',
  'mealTypes']` — `servings` is not required — and `validateRecipeBounds` skips absent numeric fields,
  so `POST /addRecipe` persists a recipe with no `servings`. The client assumes it exists:
  `SingleRecipe.tsx:602` computes `formatPrice(currRecipe.servingPrice * (servingSize ||
  currRecipe.servings))` → `NaN` → `formatPrice(NaN)` = "$NaN". `PrintableRecipe.tsx:174` has the same
  math.
- **Repro:** `POST /api/addRecipe` with the four required fields plus `servingPrice: 500` and no
  `servings` key → 201; open the recipe page → price line shows "$NaN total."
- **Fix direction:** Require `servings` server-side, and/or guard `formatPrice` against `NaN`.

#### L4 — `POST /reports` stores `reportedUsername` verbatim (any casing) while rename-propagation and admin tallies match it case-sensitively
- **File:** `server/routes/reports.js:158`
- **Subsystem:** moderation
- **What's wrong:** The route validates the handle case-insensitively (and has the canonical
  `reportedDoc.username` in hand) but persists the caller's raw string. Downstream assumes canonical
  casing with exact matches: rename propagation (`auth.js:196` `updateMany({ reportedUsername:
  prevUsername })`) and `enrichUsers` (`admin.js:129`) are case-sensitive.
- **Failure scenario:** A report filed as `reportedUsername: 'BADUSER'` against `baduser` survives
  validation but is invisible to both consumers. After `baduser` renames, the report keeps the dead
  handle; the queue's "Take down" 404s. If the freed handle is re-registered, a takedown targets the
  wrong user's review.
- **Repro:** `POST /api/reports` with altered casing, then have the target rename → `db.reports` still
  carries the old-cased handle and the queue's Take down returns 404.
- **Fix direction:** One line — store `reportedDoc.username` instead of the raw input.

#### L5 — Deleting a recipe (or account) does not cascade to its reports: open reports outlive the content
- **File:** `server/util/teardownRecipe.js:18`
- **Subsystem:** moderation
- **What's wrong:** `teardownRecipeDocs` removes the recipe, ratings, and saved/made refs but never
  touches the `reports` collection. Open reports (including the system automod hold report of an
  active hold) stay `open` forever until an admin closes each one. The delete route checks only
  ownership, not status, so an owner can delete their own `pending_review` recipe and orphan its
  automod report.
- **Repro:** File a report against recipe R, then as R's owner `DELETE /api/deleteRecipe?recipeId=R` →
  `GET /api/reports?status=open` still shows the report with `target.recipe` null.
- **Note:** The intent skeptic refuted this as anticipated/acceptable (the queue was built to render
  "Recipe no longer exists" rows, and D6 in `DATA_INTEGRITY_AUDIT.md` deliberately preserves moderation
  records over deletion). Code+reach confirmed the mechanism; likely **won't-fix** by design — verify
  against D6 before acting.

#### L6 — `GET /reports` paging is unclamped (NaN/negative/unbounded `perPage`)
- **File:** `server/routes/reports.js:186`
- **Subsystem:** moderation
- **What's wrong:** `skip = parseInt(page) * parseInt(perPage)` / `limit = parseInt(perPage)` with no
  NaN/negative/max clamp. `bugReports.js:102` clamps the identical pattern (with a comment explaining
  why) but the fix was never back-ported. `?page=abc` → `skip(NaN)` → 500; no `MAX_PER_PAGE`, and each

- **Repro:** As admin, `curl '…/api/reports?page=abc'` → 500; `'…/api/reports?perPage=100000'` →
  unbounded scan + N+1 queries.
- **Note:** Admin-only. `docs/API_CONTRACT.md:780` documents the asymmetry as known DRIFT. Back-port
  the `bugReports.js` clamp.

#### L7 — Negative `recipesPerPage` on public `/getPublicProfileRecipes` produces a negative Mongo skip and a 500
- **File:** `server/routes/publicProfile.js:168`
- **Subsystem:** gamification (public-profile)
- **What's wrong:** The route floors `page` at 0 (its comment explains why) but only upper-clamps
  `recipesPerPage` via `Math.min(...)`, so a negative like `-5` passes through; with `page >= 1`,
  `.skip(pageNum * perPage)` is negative → MongoDB rejects → 500. Unauthenticated endpoint.
- **Repro:** `curl '…/api/getPublicProfileRecipes?username=<existing>&page=1&recipesPerPage=-5'` → 500.
- **Fix direction:** `Math.max(1, …)` (or floor at a sane minimum) on `recipesPerPage`.

#### L8 — Account "Saved" tab badge and Collector/saved XP count moderation-hidden recipes that the saved list itself excludes
- **File:** `server/util/accountCounts.js:13`
- **Subsystem:** gamification
- **What's wrong:** `getAccountCountsFor` computes `saved` as the raw `$size` of `savedRecipes` with no
  visibility filter, and this one function feeds both the account tab badges and gamification
  XP/achievements. But the saved-list endpoint filters to `RECIPE_VISIBLE`. Soft-hidden recipes are
  not pulled from `savedRecipes` on takedown (only full deletion runs teardown), so the counts diverge.
- **Repro:** Save 25 recipes, `PATCH /api/admin/recipes/:id/moderation {status:'hidden'}` on one →
  badge shows 25, Saved tab lists 24, "Collector — Saved 25 recipes" achievement persists.
- **Fix direction:** Filter `saved` by visibility on the paths that render/reward it (or accept as
  minor — see L9, same root).

#### L9 — "All saved" count uses raw `savedRecipes` array size while the grid and collection badges count only visible recipes
- **File:** `server/util/accountCounts.js:19`
- **Subsystem:** saved-recipes
- **What's wrong:** Same root as L8. `getAccountCountsFor.saved` is `$size` of the raw array (includes
  soft-hidden), while `GET /getSavedRecipes` `totalCount` and collection badges filter by

- **Repro:** Save 3 recipes, hide one via admin → `GET /getAccountCounts` `saved: 3` vs

#### L10 — `MAX_COLLECTIONS` cap is only enforced by a non-atomic pre-read, so concurrent creates with distinct names can exceed 50
- **File:** `server/routes/collections.js:113`
- **Subsystem:** saved-recipes
- **What's wrong:** `POST /collections` checks `existing.length >= MAX_COLLECTIONS` on a snapshot read,

- **Repro:** `Promise.all` of 30 `POST /api/collections` with unique names against an account at 49
  collections → `GET /api/collections` returns >50.
- **Note:** Overshoot is bounded to one concurrent burst (post-burst requests fail the pre-read), so

#### L11 — Saved tab strands on a deleted collection's filter when the collections list becomes empty, showing "No Recipes Saved Yet" to a user with saves

- **Subsystem:** saved-recipes
- **What's wrong:** The dead-filter recovery effect only resets when `collections.length > 0`. If the

  fails, `activeCollectionId` keeps pointing at the dead id, the grid fetches 0 results, and (since

- **Repro:** Two tabs on Account → Saved; select the only collection in tab A; delete it in tab B;
  refocus tab A.
- **Fix direction:** Reset `activeCollectionId` when the active collection is gone regardless of
  `collections.length`.

## Refuted (verified NOT a real bug)

#### R1 — `PATCH /recipes/:recipeId/collections` reports success even when a lost race means the requested `collectionIds` were never persisted
- **File:** `server/routes/collections.js:288` · **Subsystem:** saved-recipes
- **Why refuted:** The code path genuinely swallows a lost-race `E11000` without applying
  `collectionIds` and reports success, but no realistic flow reaches it. The only caller
  (`AddToCollectionPopover`) can't fire the PATCH until two later-initiated round trips complete, which
  essentially guarantees the earlier `POST /save` has landed; triggering the bug needs a request
  anomalously delayed past those round trips **and** arriving inside the millisecond
  `findOne`→`updateOne` gap. Even if hit, impact is one recoverable dropped tag on the user's own data.
  A lab-repro race, not a practically reachable failure.

## Additional findings (resume run)

These come from the resume run (2026-07-10) that completed the three subsystems the first run couldn't
reach, plus two gamification angles the first run's finder didn't surface. Same 2-of-3 adversarial-verify

### Auth

#### A1 — `setUsername` rename propagation is non-transactional and non-idempotent on retry, permanently orphaning denormalized handles
- **File:** `server/routes/auth.js:191` · **Severity:** low · **Votes:** code✓ reach✓ intent✗
- **What's wrong:** In `POST /setUsername` the canonical write to `usernames` (line 165) commits
  **first**, then the denormalized-handle propagation to `ratings.username` (193) and
  `reports.reportedUsername` (196) runs afterward, outside any transaction, guarded by
  `if (prevUsername && prevUsername !== username)`. If the `usernames` write succeeds but a later
  `updateMany` throws (transient blip) → 500, yet the username is already changed. On retry with the
  same name, `prevUsername === username`, so the whole propagation block is **skipped** and the
  old-handle rows are never reconciled.
- **Failure scenario:** `alice` → `bob`; `usernames` updates; `ratings.updateMany` hits a transient
  error → 500. User retries `bob`; propagation is skipped; reviews keep `ratings.username = 'alice'`
  forever, so the review links under `alice` and `/u/alice` 404s.
- **Note:** The intent skeptic refuted this — `DATA_INTEGRITY_AUDIT.md` **D3** explicitly accepts it as
  a display-only residual (review identity is uid-keyed after D1, so editability/moderation are
  unaffected). Confirmed on the mechanism (code+reach); treat as **documented won't-fix** unless D3 is
  revisited. Requires a transient DB error mid-request.

### Ingredient parsing

#### I1 — `parseLimiter` (30/min) is below the 50-ingredient max, and the frontend ignores the `RATE_LIMITED` code, so large-recipe entry silently drops price/image on the excess ingredients
- **File:** `server/routes/ingredients.js:71` · **Severity:** medium · **Votes:** code✓ reach✓ intent✓
- **What's wrong:** `POST /api/ingredients/parse` is limited to the factory default 30/60s, but
  `MAX_INGREDIENTS = 50` and the add-recipe flow fires one parse request per ingredient (plus edits and
  per-row Retry). The server's own comment claims "30/min comfortably covers … max 50 per recipe" — the
  math doesn't hold. On the 31st request in a rolling minute the server returns 429 with
  `code: 'RATE_LIMITED'` (comment says the FE should branch on it), but `getIngredientData`
  (`src/api/recipes.ts:609`) just returns the generic error variant — **no code in `src/` references
  `RATE_LIMITED`**. The row lands as errored with no price/image and a misleading "Retry or edit it"
  toast, and Retry immediately re-429s. Worse: `calculateServingPrice` sums only non-null
  `ingredientData`, so each rate-limited ingredient contributes $0 → the **persisted** `servingPrice`
  silently understates the true cost.
- **Failure scenario:** A user builds a 40-ingredient recipe within ~60s. Requests 31–40 get 429; those
  rows show "—" price; Retry re-fails for up to a minute; if they publish anyway the stored
  `servingPrice` (shown on cards and the recipe page) omits 10 ingredients with no indication.
- **Repro:** Add >30 ingredients within 60s → the 31st-onward rows error with "Couldn't fetch data",
  Retry re-fails, and the Est./serving figure omits their cost.
- **Fix direction:** Raise the parse limiter above the ingredient cap (with headroom for edits/retries),
  and/or have the FE branch on `RATE_LIMITED` with a backoff + accurate messaging.

#### I2 — `closestFraction` snaps every non-integer quantity to one of 9 fractions and never rounds up past 7/8, silently distorting displayed amounts
- **File:** `src/util/formatQuantity.ts:22` · **Severity:** low · **Votes:** code✓ reach✓ intent✗
- **What's wrong:** `closestFraction` returns a whole number only when the decimal part is exactly 0;
  otherwise it snaps to the nearest of a fixed 9-entry table capped at 7/8 = 0.875. So (a) any decimal
  in `[0.9375, 1.0)` renders as "7/8" instead of rounding up to the next whole number, and (b) every
  non-"nice" quantity shows up to ~1/16 error. This is the sole quantity renderer on the recipe page,
  printable view, and add-recipe row. `parseIngredientString` returns literal decimals (e.g.
  `0.95 lb` → `0.95`), so directly-entered ingredients are affected, not just scaled ones.
- **Failure scenario:** `0.95 lb chicken` renders as "7/8 lb chicken" — an ~8% understatement with no
  round-up.
- **Repro:** Add `0.95 lb chicken` (or scale a recipe into `[0.9375, 1)`) → quantity shows "7/8".
- **Fix direction:** Round up to the next whole number when the fractional remainder exceeds the
  largest table entry (or widen/repair the fraction table).

#### I3 — Ingredient ranges (e.g. "2-3 cups") are silently flattened to the low end everywhere they are displayed
- **File:** `src/pages/SingleRecipe/SingleRecipe.tsx:214` · **Severity:** low · **Votes:** code✓ reach✓ intent✓
- **What's wrong:** `parseIngredientString` captures range bounds in `minQty`/`maxQty` (e.g.
  `2-3 cups flour` → `quantity 2, minQty 2, maxQty 3`), and `ParsedIngredient` carries both fields
  (`src/types.ts:16-17`). But no renderer reads them — `SingleRecipe` (214), `PrintableRecipe` (103–105),
  and `IngredientItemText` (23) all display only `quantity` (the low end), and `updateIngredients` only
  scales `quantity`. The upper bound is captured, stored, then dropped from every view.
- **Failure scenario:** `2-3 cups flour` renders everywhere as "2 cups flour", discarding the "-3".
- **Repro:** Add `2-3 cups flour`, view/print → only "2 cups flour" shows.
- **Fix direction:** Render the `minQty`–`maxQty` range when present (and scale both bounds).

### Gamification (additional)

#### G1 — Achievement + XP counts include unpublished/hidden/pending recipes, so "Published N recipes" awards never revoke and overstate
- **File:** `server/util/accountCounts.js:24` · **Severity:** medium · **Votes:** code✓ reach✓ intent✓
- **What's wrong:** `getAccountCountsFor` counts recipes with `countDocuments({ userId })` — **no status
  filter** — and this feeds `computeXp` (100 XP each) and the `first_recipe`/`prolific` tests, whose copy
  is "Published your first recipe" / "Published 10 recipes". The `recipes` collection contains
  non-published statuses (`unpublished` from editorial de-publish, `hidden` from takedown,
  `pending_review` from automod holds), none excluded, so they still count as "Published" and grant
  XP/level.
- **Failure scenario:** A user publishes 10 recipes (earns "Prolific Author", ~1000 XP); all 10 are then
  unpublished/hidden. `counts.recipes` stays 10, so they keep "Prolific Author — Published 10 recipes"
  and the level despite zero published recipes. Conversely a user whose only recipe is `pending_review`
  still shows "First Recipe" earned.
- **Repro:** Create 1 active recipe → `getGamification` shows `first_recipe` + 100 XP. Set it
  `unpublished`/`pending_review` → `getGamification` still shows `first_recipe` earned, XP unchanged.
- **Fix direction:** Count only publicly-visible recipes for XP/achievements (mirror `RECIPE_VISIBLE`);
  relates to **M7** (same unfiltered-count root on the public path).

#### G2 — "Left N reviews" achievements count star-only ratings that have no review text
- **File:** `server/util/accountCounts.js:26` · **Severity:** low · **Votes:** code✓ reach✓ intent✗
- **What's wrong:** The `ratings` count is `countDocuments({ userId })` over the shared ratings
  collection, where a doc can be rating-only (`reviewText: ''`). This drives XP (15 each) and the
  `first_review`/`critic` achievements whose copy is "Left your first review" / "Left 10 reviews". A
  star rating with no text is not a review, yet counts toward the review achievements.
- **Failure scenario:** A user star-rates 10 recipes and writes no text → `counts.ratings = 10` → unlocks
  "Critic — Left 10 reviews" and fires the toast, having authored zero reviews.
- **Repro:** `POST /addRating` for 10 recipes with no reviews → `getGamification` shows `critic` in
  `earned`/`newlyUnlocked`.
- **Fix direction:** Count only docs with non-empty `reviewText` for the review achievements.

### Drafts

#### D1 — Transient draft-load failure leaves `draftId` set with an empty form; publishing then silently deletes the unloaded draft
- **File:** `src/pages/AddRecipe/useRecipeForm.ts:270` · **Severity:** medium · **Votes:** code✓ reach✓ intent✓
- **What's wrong:** Resuming a draft initializes `draftId` to X, then the hydration effect calls
  `getDraft(X)`. On a genuine 404/403 it correctly clears `draftId`, but on a **transient** error
  (network/5xx) it only toasts ("Could not load your draft. Refresh to try again.") and leaves
  `draftId === X` with `hydrated` false. Autosave is safely gated on `hydrated`, but `handleSubmit`'s
  create path is **not** — if the user builds and publishes a recipe in the empty form, `handleSubmit`
  reaches `clearDraft()` (line 450), which does `DELETE /api/drafts/X` — deleting a draft whose real
  content was never loaded.
- **Failure scenario:** User clicks "Continue editing" on draft X (a full recipe); `getDraft(X)` hits a
  transient 500; form stays empty, `draftId = X`; user re-enters a different recipe and publishes →
  `clearDraft()` → draft X permanently lost, though it was never opened.
- **Repro:** Autosave a real draft (id X); load `/add-recipe?draftId=X` while the GET returns 5xx/offline;
  ignore the toast, fill a new recipe, click Create → recipe publishes and draft X is gone.
- **Fix direction:** Gate the create path's `clearDraft()` on `hydrated` (don't delete a draft that
  never loaded).

#### D2 — Draft `PUT` does a full-document `$set` with no version/precondition — two tabs editing the same draft silently lose one tab's edits
- **File:** `server/routes/drafts.js:112` · **Severity:** low · **Votes:** code✓ reach✓ intent✗
- **What's wrong:** `PUT /drafts/:id` overwrites every whitelisted field with the client's full payload
  via `$set`, and the client always sends the complete `draftContent`. No optimistic-concurrency guard
  (no `updatedAt`/version precondition), so concurrent editors last-write-wins-clobber rather than merge.
- **Failure scenario:** Draft X open in Tab A and Tab B. Tab A adds 5 ingredients (autosave PUTs full
  body). Tab B (stale content) tweaks the title; its autosave PUTs a full body whose ingredient array
  lacks Tab A's additions → Tab A's 5 ingredients silently erased.
- **Repro:** Resume the same draft in two tabs; add ingredients in A (wait for "Draft saved"); change the
  title in B (wait for "Draft saved"); reload → A's additions are gone.
- **Fix direction:** Add an `updatedAt`/version precondition to the update and surface a conflict.

#### D3 — Recipe content entered before any title is never autosaved and is lost on navigation/refresh
- **File:** `src/pages/AddRecipe/useDraftAutosave.ts:107` · **Severity:** low · **Votes:** code✓ reach✓ intent✗
- **What's wrong:** Draft **creation** is gated on a non-blank title (`canCreateDraft = !!title.trim()`).
  Until a title is typed, no draft exists and the unmount flush also no-ops, so description, all
  ingredients, all instructions, times, cuisine, and diet tags entered first are never persisted. This
  intentionally gates out stray-keystroke throwaway drafts, but a user who fills substantial content
  before the title loses all of it.
- **Failure scenario:** User pastes 12 ingredients + 8 instruction steps + a description intending to name
  the recipe last, then accidentally closes the tab (or the token expires and they refresh) → no draft
  was ever created → all work gone.
- **Repro:** On `/add-recipe`, leave Title empty, add ingredients/instructions/description; the "Draft
  saved" indicator never appears; refresh → everything gone.
- **Fix direction:** Trigger draft creation on any substantive content (not title alone), or warn on
  unload when unsaved content exists without a title.
